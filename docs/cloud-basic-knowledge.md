# AWS 웹 서비스 배포 미션 — 용어와 핵심 개념 정리

이 문서는 「내가 만든 웹사이트를 인터넷에 올려 누구나 쓰게 하기」 실습과 평가 질문을 바탕으로 작성한 초보자용 학습 자료다. 실제 실습은 Ubuntu EC2 한 대에 Nginx 기본 페이지를 배포한 뒤, 검증 증거를 확보하고 자원을 정리하는 범위였다.

## 1. 이 미션에서 배운 것

**프로그램을 인터넷상의 컴퓨터에서 실행하고, 사람들이 접속할 수 있는 경로와 접근 권한을 구성하는 방법**을 배운 미션이다.

파이썬 미션은 주로 프로그램 내부의 기능을 만들었다. 이번에는 프로그램을 둘 컴퓨터, 네트워크, 보안, 실행 상태 확인, 오류 해결, 자원 정리를 다뤘다. 웹페이지는 그 환경이 작동한다는 것을 확인하는 결과물이었다.

| 단계 | 우리가 한 일 | 이해할 핵심 |
|---|---|---|
| 컴퓨터 마련 | EC2 생성 | 내 PC가 아닌 다른 컴퓨터에서 실행 |
| 네트워크 마련 | VPC·서브넷 생성 | 서버가 사용할 주소 공간 구성 |
| 인터넷 연결 | IGW·라우팅 설정 | 목적지까지 갈 경로 구성 |
| 접근 제한 | SG·IAM 설정 | 접속과 관리 작업의 권한 구분 |
| 서비스 실행 | Nginx 설치 | 요청을 처리할 프로그램 필요 |
| 검사 | SSH·curl·브라우저 | 서로 다른 위치에서 작동 확인 |
| 종료 | EC2·EBS·IGW·VPC 정리 | 사용이 끝난 자원을 추적하고 제거 |

## 2. 컴퓨터와 실행 환경 용어

| 용어 | 뜻 | 이번 실습에서의 예 |
|---|---|---|
| AWS | Amazon Web Services. 컴퓨터·네트워크·저장소 등 IT 자원을 제공하는 클라우드 서비스 | 실습 환경을 만든 서비스 |
| 클라우드 | 필요한 IT 자원을 네트워크를 통해 제공받아 사용하는 방식 | 물리 서버를 직접 구매하지 않고 EC2 사용 |
| 서버 | 다른 프로그램이나 사용자에게 기능을 제공하는 컴퓨터 또는 프로그램 | EC2 컴퓨터와 Nginx 웹 서버 |
| 클라이언트 | 서버에 요청하는 프로그램 또는 기기 | 노트북의 브라우저, SSH 클라이언트 |
| EC2 | Elastic Compute Cloud. AWS에서 가상 서버를 만들어 사용하는 서비스 | 웹 서버용 컴퓨터 마련 |
| 인스턴스 | EC2에서 실제로 생성한 가상 서버 한 대 | codyssey-web-server |
| 인스턴스 유형 | 가상 서버의 CPU·메모리 등 사양을 정하는 구분 | t3.micro |
| AMI | Amazon Machine Image. 운영체제 등 서버 시작에 필요한 이미지 | Ubuntu Server 이미지 |
| 운영체제(OS) | 프로그램 실행과 CPU·메모리·파일 등을 관리하는 기본 소프트웨어 | 서버는 Ubuntu, 노트북은 Windows |
| Ubuntu | Linux 기반 운영체제의 한 종류 | Ubuntu 24.04.4 LTS |
| LTS | Long Term Support. 장기 지원을 제공하는 릴리스 구분 | 실습에 Ubuntu LTS 사용 |
| 리전(Region) | AWS 자원이 배치되는 지리적 지역 | 서울, ap-northeast-2 |
| 가용 영역(AZ) | 리전 안에서 장애 영향을 분리하도록 설계된 데이터센터 집합 단위 | ap-northeast-2a |
| 배포(Deployment) | 프로그램을 사용할 환경에 설치·설정하고 실행 가능한 상태로 만드는 일 | EC2에 Nginx 설치·실행 |

**EC2와 Nginx는 다르다.** EC2는 컴퓨터를 제공하고, Nginx는 그 컴퓨터에서 웹 요청을 처리한다. EC2만 켠다고 웹페이지가 자동으로 제공되지는 않는다.

**리전과 가용 영역도 다르다.** 서울이 리전이고, 그 안에 여러 AZ가 있다. AZ를 정확히 건물 한 채라고 생각하면 안 된다.

## 3. 네트워크 용어

### 3-1. VPC와 서브넷

| 용어 | 뜻 | 실습 예 |
|---|---|---|
| 네트워크 | 컴퓨터들이 데이터를 주고받도록 연결된 구조 | EC2와 인터넷 사이의 연결 |
| VPC | Virtual Private Cloud. AWS 계정에서 구성하는 논리적으로 분리된 가상 네트워크 | codyssey-vpc, 10.0.0.0/16 |
| 서브넷(Subnet) | VPC 주소 공간을 나눈 구역. AWS 서브넷은 하나의 AZ에 속함 | 10.0.1.0/24 |
| 퍼블릭 서브넷 | 연결된 라우팅 테이블에 IGW로 향하는 직접 경로가 있는 서브넷 | 이번 EC2가 들어간 서브넷 |
| 프라이빗 서브넷 | IGW로 향하는 직접 경로가 없는 서브넷 | 이번에는 구성하지 않음 |

VPC를 단지, 서브넷을 단지 안의 구역으로 비유할 수 있다. 다만 실제로는 건물이 아니라 네트워크와 IP 주소 범위를 나누는 설정이다.

**서브넷 이름에 public을 붙인다고 퍼블릭 서브넷이 되지 않는다.** 라우팅 설정이 중요하다. 또한 퍼블릭 서브넷 안의 서버라도 IPv4 인터넷 통신을 하려면 퍼블릭 IP와 적절한 접근 규칙 등이 필요하다.

### 3-2. IP 주소와 CIDR

| 용어 | 뜻 | 실습 예 |
|---|---|---|
| IP 주소 | 네트워크에서 통신 대상을 식별하는 주소 | 서버의 10.0.1.165 |
| IPv4 | 32비트 주소 체계. 보통 숫자 네 묶음으로 표현 | 10.0.1.165 |
| 프라이빗 IP | 내부 네트워크에서 사용하는 사설 주소 | EC2의 10.0.1.165 |
| 퍼블릭 IP | 공용 인터넷에서 통신에 사용하는 주소 | 실습 당시 3.38.108.17 |
| CIDR | 주소와 접두사 길이로 IP 범위를 나타내는 표기 | 10.0.1.0/24 |
| /32 | IPv4 주소 하나를 나타내는 접두사 길이 | SSH 허용 대상 하나 |
| 0.0.0.0/0 | 모든 IPv4 주소를 포괄하는 범위 | 기본 경로 또는 모든 IPv4 소스 |

IPv4는 32비트다. `/24`는 앞의 24비트를 네트워크 부분으로 고정한다는 뜻이다. 뒤에 남은 비트가 많을수록 주소 범위가 넓다.

| 표기 | 포함 범위 | 전체 주소 개수 |
|---|---|---|
| 10.0.0.0/16 | 10.0.0.0 ~ 10.0.255.255 | 65,536 |
| 10.0.1.0/24 | 10.0.1.0 ~ 10.0.1.255 | 256 |
| 121.135.181.35/32 | 121.135.181.35 하나 | 1 |

주소 개수와 실제 EC2에 할당할 수 있는 개수는 다르다. AWS는 일반 IPv4 서브넷에서 일부 주소를 예약하므로 모든 주소를 서버에 할당할 수는 없다.

사설 IP는 여러 독립된 네트워크에서 반복해서 사용될 수 있다. 집과 AWS에서 같은 사설 주소가 보인다고 같은 컴퓨터라는 뜻은 아니다.

### 3-3. Gateway, IGW와 라우팅

**Gateway(게이트웨이)는 서로 다른 네트워크 사이의 통신을 이어주는 출입구 역할을 가리키는 말**이다. 모든 게이트웨이가 AWS의 Internet Gateway인 것은 아니다.

| 용어 | 뜻 | 실습에서 한 일 |
|---|---|---|
| IGW | Internet Gateway. VPC와 인터넷의 통신을 가능하게 하는 AWS 구성 요소 | codyssey-igw를 VPC에 연결 |
| 라우팅(Routing) | 목적지 주소에 따라 데이터를 보낼 경로를 선택하는 일 | 외부 목적지는 IGW로 보냄 |
| 라우팅 테이블 | 목적지 범위와 다음 대상을 적은 경로표 | codyssey-public-rt |
| 기본 경로 | 더 구체적인 경로가 없는 목적지에 적용할 경로 | 0.0.0.0/0 → IGW |
| local 경로 | VPC 내부 통신에 사용하는 경로 | 10.0.0.0/16 → local |
| 서브넷 연결 | 특정 서브넷이 사용할 라우팅 테이블을 지정하는 것 | public-subnet과 public-rt 연결 |
| Attached / Detached | 연결됨 / 분리됨 | IGW를 VPC에 연결·분리 |

실습 경로표:

| 목적지 | 다음 대상 | 의미 |
|---|---|---|
| 10.0.0.0/16 | local | VPC 내부 통신 |
| 0.0.0.0/0 | IGW | 나머지 IPv4 목적지에 대한 기본 경로 |

여러 경로가 맞으면 일반적으로 **더 구체적인 주소 범위가 우선**한다. 10.0.1.165는 두 경로에 모두 포함되지만 `/16`이 `/0`보다 구체적이므로 local 경로를 선택한다.

라우팅 테이블은 통신 중간에 놓이는 별도 서버가 아니다. 어디로 보낼지를 정하는 규칙이다. IGW 연결만 하고 서브넷 경로표에 반영하지 않으면 인터넷 경로 설정이 완성되지 않는다.

### 3-4. DNS, localhost, 포트

| 용어 | 뜻 | 실습 예 |
|---|---|---|
| DNS | 이름을 IP 주소 등 DNS 레코드로 조회하는 체계 | example.com을 주소로 조회 |
| 도메인 이름 | 사람이 사용하기 쉬운 이름 | example.com |
| localhost | 명령어를 실행 중인 컴퓨터 자신을 가리키는 이름 | SSH 안에서는 EC2 자신 |
| 루프백 주소 | 자기 자신에게 통신하는 주소 | 127.0.0.1 |
| 포트 | 한 컴퓨터 안에서 통신할 프로그램·서비스를 구분하는 번호 | SSH 22, HTTP 80 |
| TCP | 연결을 기반으로 신뢰성 있는 데이터 전달을 제공하는 전송 프로토콜 | SSH와 이번 HTTP 연결 |
| 인바운드 | 대상 서버로 들어오는 통신 | 브라우저 → EC2 |
| 아웃바운드 | 대상 서버에서 나가는 통신 | EC2 → example.com |

**localhost는 항상 내 노트북을 뜻하지 않는다.** Windows에서 실행하면 Windows 자신이고, SSH로 들어간 Ubuntu에서 실행하면 Ubuntu 서버 자신이다.

IP를 건물 주소, 포트를 그 건물의 서비스 창구 번호로 비유할 수 있다. 주소가 맞아도 필요한 포트의 서비스가 실행되지 않으면 원하는 응답을 받을 수 없다.

## 4. 보안과 권한 용어

### 4-1. Security Group과 IAM

| 용어 | 뜻 | 실습 적용 |
|---|---|---|
| Security Group(SG) | 네트워크 인터페이스에 적용하는 상태 기반 트래픽 허용 규칙 | HTTP 80 전체, SSH 22 내 IP |
| 방화벽 | 통신을 규칙에 따라 허용·차단하는 기능의 일반적인 이름 | SG는 방화벽 역할을 함 |
| IAM | Identity and Access Management. AWS 사용자·역할·작업 권한 관리 | codyssey-student 권한 설정 |
| IAM 사용자 | AWS에 접근하는 하나의 사용자 신원 | codyssey-student |
| 정책(Policy) | 허용·거부할 작업과 대상·조건 등을 적은 규칙 | CodysseyCloudLabSeoul |
| 역할(Role) | 사용자나 서비스 등이 맡아 임시 자격 증명으로 사용하는 권한 신원 | 이번 사용자 방식과 구분해서 이해 |
| 최소 권한 | 필요한 작업과 대상만 허용하는 원칙 | 서울 리전의 필요한 EC2 관련 작업 |
| MFA | 로그인에 여러 인증 요소를 사용하는 방식 | 비밀번호와 인증 앱 |

**SG는 “서버의 문으로 어떤 통신이 들어올 수 있는가”, IAM은 “AWS 설정을 누가 어떻게 바꿀 수 있는가”를 제어한다.** IAM이 허용됐다고 SSH가 연결되는 것도 아니고, SSH 22를 열었다고 AWS 콘솔에서 서버를 삭제할 수 있는 것도 아니다.

SG는 허용 규칙을 사용하며, 허용 규칙이 없는 인바운드는 허용하지 않는다. 상태 기반이므로 허용된 연결의 응답 트래픽을 추적한다. 웹 응답을 위해 방문자의 임시 포트를 인바운드로 전부 열 필요는 없다.

### 4-2. 비슷해 보여도 서로 다른 사용자와 열쇠

| 구분 | 어디에서 쓰는가 | 이번 예 |
|---|---|---|
| AWS 루트 사용자 | AWS 계정 소유자의 전체 관리 | 가입·초기 계정 준비 |
| IAM 사용자 | AWS 콘솔/API 작업 | codyssey-student |
| Ubuntu 사용자 | EC2 내부 Linux 작업 | ubuntu |
| Linux root | Linux 내부 최고 권한 사용자 | sudo로 필요한 명령 실행 |
| SSH 키페어 | 서버 SSH 로그인 인증 | codyssey-key |
| AWS 액세스 키 | AWS API 요청 인증 | 이번 로컬 SSH에는 필요 없음 |

AWS 루트와 Linux root는 이름이 같아도 다른 권한이다. `sudo apt install nginx`는 Linux 권한을 사용하는 것이지 AWS 루트로 전환하는 것이 아니다.

키페어는 공개 키와 개인 키로 구성된다. 개인 키 `.pem`은 노트북에 보관하고, 대응하는 공개 키가 서버 측 인증에 사용된다. 개인 키는 비밀번호처럼 보호해야 한다.

SSH 최초 연결 때 확인한 **서버 호스트 키**는 “접속한 서버가 누구인가”를 확인하는 데 쓰인다. `codyssey-key.pem`은 “접속하려는 사용자가 올바른 개인 키를 가졌는가”를 증명한다. 서로 다른 방향의 확인이다.

### 4-3. IAM 정책 JSON 읽기

| 항목 | 뜻 | 실습 값 |
|---|---|---|
| Version | 정책 문법 버전 | 2012-10-17, 작성 날짜가 아님 |
| Statement | 권한 규칙들의 목록 | 조회 규칙과 관리 규칙 |
| Sid | 규칙을 구분하기 위한 식별 이름 | ReadEC2AndNetworkInSeoul |
| Effect | 허용 또는 거부 | Allow |
| Action | 허용할 API 작업 | ec2:RunInstances 등 |
| Resource | 작업 대상 자원 | * |
| Condition | 규칙이 적용되는 조건 | 서울 리전 |
| aws:RequestedRegion | 요청이 향하는 AWS 리전 조건 키 | ap-northeast-2 |
| Describe* | Describe로 시작하는 조회 작업 | EC2 및 네트워크 조회 |
| ARN | AWS 자원을 식별하는 이름 체계 | 사용자 ARN 등 |

`Resource: "*"`는 나열한 작업이 모든 대상 자원에 적용될 수 있다는 뜻이지, 모든 AWS 작업을 허용한다는 뜻은 아니다. Action과 Condition도 함께 봐야 한다.

이번 정책은 서울 리전·작업 범위를 줄였지만 자원 ID/태그 단위까지 제한하지 않았다. **“최소 권한을 적용하려고 범위를 줄였다”와 “최소 범위로 완벽하게 제한했다”는 다르다.** 추가 개선으로 자원 ARN, 태그 조건, 생성 시 조건 등을 검토할 수 있지만 작업별 지원 여부를 확인해야 한다.

## 5. 저장소와 자원 관리 용어

| 용어 | 뜻 | 이번 실습 |
|---|---|---|
| EBS | Elastic Block Store. EC2에 연결하는 블록 저장소 | Ubuntu와 Nginx 파일 저장 |
| 볼륨(Volume) | 하나의 논리적인 디스크 | 8GiB gp3 |
| 루트 볼륨 | 운영체제가 설치된 볼륨 | /dev/sda1로 연결 |
| gp3 | EBS 범용 SSD 볼륨 유형 | 실습 루트 볼륨 유형 |
| GiB | 2의 거듭제곱 기준 용량 단위 | 1GiB = 1,073,741,824바이트 |
| IOPS | 초당 입출력 작업 수 | 화면에 3000 표시 |
| 처리량 | 단위 시간에 읽고 쓰는 데이터 양 | IOPS와 다른 지표 |
| 스냅샷 | 특정 시점의 볼륨 데이터를 보존하는 백업 방식 | 별도 실습 백업은 만들지 않음 |
| 종료 시 삭제 | EC2 종료 시 연결 볼륨을 삭제하도록 하는 설정 | true 필터로 확인 |
| Elastic IP(EIP) | 계정에 할당하고 연결할 수 있는 고정 퍼블릭 IPv4 주소 | 미할당 |
| 태그(Tag) | 자원에 붙이는 키·값 형태의 관리 정보 | Name과 codyssey- 이름 |
| Billing | AWS 사용량·청구 내역 관리 | 잔여 자원과 비용 확인 시 사용 |

EC2가 컴퓨터라면 EBS는 그 컴퓨터에 연결한 디스크다. **EC2를 종료한다고 모든 저장 자원이 무조건 사라지는 것은 아니다.** 볼륨의 종료 시 삭제 설정과 별도 스냅샷 등을 확인해야 한다.

### 중지와 종료

| 상태/작업 | 뜻 | 주의점 |
|---|---|---|
| Running | 서버 실행 중 | 프로그램 실행 가능 |
| Stop / Stopped | 컴퓨터를 꺼 둠 | EBS 등 자원은 남을 수 있음 |
| Start | 중지된 컴퓨터를 다시 켬 | 자동 할당 퍼블릭 IPv4가 바뀔 수 있음 |
| Reboot | 실행 중 서버 재부팅 | 종료 후 새 서버 생성과 다름 |
| Terminate / Terminated | 인스턴스 종료·삭제 | 같은 인스턴스를 다시 시작할 수 없음 |
| Release | 할당 자원 반환 | EIP 반환 때 사용하는 표현 |

이번 정리는 EC2 종료 → EBS 없음 확인 → IGW·VPC 삭제로 검증했다. EIP는 생성하지 않았으므로 “삭제했다”가 아니라 “미할당으로 정리 대상 없음”이 정확하다.

## 6. 웹과 명령어 용어

| 용어/명령 | 뜻 | 결과 해석 |
|---|---|---|
| Nginx | 웹 요청을 처리하는 서버 프로그램 | 기본 페이지 제공 |
| HTTP | 웹 요청과 응답을 주고받는 프로토콜 | 이번 외부 접속 방식 |
| HTTPS | TLS로 보호되는 HTTP 통신 | 외부 example.com 검사에 사용 |
| TLS | 통신 암호화와 상대 인증 등을 제공하는 기술 | HTTPS의 기반 |
| 인증서 | 서버 이름과 공개 키 등의 정보를 인증하는 자료 | HTTPS 구성 때 필요 |
| GET | 자원의 내용을 요청하는 HTTP 메서드 | 브라우저 페이지 요청 |
| HEAD | 본문 없이 헤더를 요청하는 HTTP 메서드 | curl -I |
| 200 OK | 해당 요청이 성공했다는 HTTP 응답 | 정상 웹 응답 |
| /health | 서비스 상태 확인에 흔히 사용하는 경로 이름 | 선택하지 않은 B 방식 |
| SSH | 암호화된 원격 접속 프로토콜 | 노트북에서 Ubuntu 관리 |
| PowerShell | Windows의 명령 실행 셸 | SSH 실행 출발점 |
| 터미널 | 명령어 입출력을 보여주는 환경 | PowerShell·SSH 작업 화면 |
| sudo | 다른 사용자, 보통 root 권한으로 명령 실행 | 패키지 설치 |
| apt update | 패키지 목록 갱신 | 프로그램 전체 업그레이드와 다름 |
| apt install | 패키지 설치 | nginx 설치 |
| systemctl | 서비스 등을 관리하는 명령 | Nginx 실행 상태 확인 |
| enable --now | 부팅 시 자동 시작 설정과 즉시 시작 | Nginx 서비스 활성화 |
| is-active | 서비스 현재 실행 상태 확인 | active |
| curl | URL로 요청을 보내는 명령 도구 | HTTP 응답 검사 |
| whoami | 현재 명령 실행 사용자 표시 | SSH 안에서는 ubuntu |
| hostname | 현재 컴퓨터 이름 표시 | ip-10-0-1-165 |
| icacls | Windows 파일 접근 권한 관리 | 개인 키 ACL 수정 |
| ACL | Access Control List. 접근 권한 목록 | 키 파일을 누가 읽는지 제어 |
| 로그(Log) | 프로그램의 동작·오류 기록 | 원인 분석의 근거 |

**200은 전체 시스템이 완벽하다는 뜻이 아니다.** 해당 시점의 해당 요청이 성공했다는 증거다. 부하, 다른 경로, 재부팅 후 동작까지 모두 증명하지 않는다.

`systemctl is-active`가 active라고 해도 재부팅 후 자동 실행 설정까지 증명하는 것은 아니다. 자동 시작 설정은 `systemctl is-enabled nginx`로 별도 확인할 수 있다. 이 명령은 학습용 추가 확인 방법이며 이미 실행했다고 기록하지 않는다.

## 7. 가장 헷갈리기 쉬운 구분

| 질문 | 답 |
|---|---|
| VPC만 만들면 인터넷 연결이 되는가? | 아니요. IGW·라우팅·IP·접근 규칙 등이 필요합니다. |
| 퍼블릭 서브넷에 있으면 모든 포트가 공개되는가? | 아니요. SG와 서비스 실행 여부 등도 작용합니다. |
| HTTP를 전체 허용하면 SSH도 전체 허용되는가? | 아니요. 포트별 규칙이 다릅니다. |
| IAM에 서버 삭제 권한이 있으면 SSH도 되는가? | 아니요. 네트워크와 SSH 인증을 별도로 충족해야 합니다. |
| 노트북을 끄면 웹사이트도 꺼지는가? | EC2에서 실행 중이면 노트북과 독립적으로 동작합니다. |
| HTTP 주소의 안전하지 않음은 해킹됐다는 뜻인가? | 아니요. HTTPS로 보호되지 않는 접속이라는 의미입니다. |
| curl -I가 성공하면 GET /health 검증인가? | 아니요. HEAD 요청이며 경로도 다릅니다. 우리는 브라우저 A 방식을 택했습니다. |
| EC2 중지가 자원 정리 완료인가? | 아니요. EBS 등 남은 자원을 확인해야 합니다. |
| 삭제 전 설정 화면이 삭제 완료 증거인가? | 아니요. 실제 종료·삭제 후 상태를 확인해야 합니다. |

## 8. 평가 질문을 보고 더 생각해볼 점

### 8-1. 길이 있는 것과 문이 열린 것은 다르다

라우팅은 경로, SG는 통신 허용 여부다. 경로가 있어도 포트를 막으면 통신하지 못하고, 포트를 열어도 경로가 없으면 도달하지 못한다. 문 안에서 요청을 처리할 Nginx도 필요하다.

생각해보기: Nginx가 active이고 localhost 200인데 외부 접속만 실패한다면 무엇부터 볼까?

답: 연결된 서브넷 경로표, IGW 연결, SG 80, 현재 퍼블릭 IP를 우선 확인한다. 이것만으로 원인을 확정하지는 않는다.

### 8-2. 같은 오류처럼 보여도 실패한 단계가 다르다

| 증상 | 우선 점검할 곳 |
|---|---|
| SSH timeout | IP·라우팅·SG·서버 상태 |
| Connection refused | 대상에 도달했지만 서비스 미실행 또는 거부 가능성 |
| bad permissions | 로컬 개인 키 파일 ACL |
| Permission denied (publickey) | 사용자 이름·키·키 사용 실패의 앞선 메시지 |
| AWS AccessDenied | IAM 정책·조건·다른 권한 제한 |
| localhost 200, 외부 실패 | 서버 밖의 경로·주소·접근 제어 |

표는 출발점이지 오류 하나와 원인을 1:1로 단정하는 규칙이 아니다. 이번에는 publickey 앞에 bad permissions가 있었으므로 로컬 ACL을 먼저 고쳤다.

### 8-3. 설정값보다 설정한 이유를 설명하기

“0.0.0.0/0을 입력했다”에서 끝내지 않고 “웹페이지는 모든 IPv4 사용자가 접근하도록 했기 때문”이라고 설명한다. 같은 값이 라우팅에서는 목적지 범위이고 SG 인바운드에서는 소스 범위라는 점도 구분해야 한다.

### 8-4. 자원 이름보다 ID가 더 정확하다

이름은 중복되거나 바뀔 수 있다. Name 태그는 사람이 알아보기 좋게 하고, 실제 삭제 대조는 ID와 연결 관계로 확인한다. 이번에는 codyssey- 이름과 ID를 함께 기록하여 다른 VPC를 남겼다.

### 8-5. 최소 권한과 편의의 균형

모든 권한을 주면 실습은 쉽게 진행될 수 있지만, 실수 범위도 커진다. 반대로 필요한 조회까지 모두 막으면 문제 진단이 어려울 수 있다. 작업에 필요한 조회와 변경을 구분하고, 거부된 작업의 이유를 확인해서 범위를 조정하는 연습이 중요하다.

### 8-6. 서버가 두 대면 무조건 두 배 빠를까?

아니다. 트래픽을 두 서버로 나눠야 하고, 병목이 DB나 외부 API이면 EC2만 늘려도 해결되지 않을 수 있다. 사용자의 파일·세션이 한 서버에만 있으면 다른 서버로 이동했을 때 결과가 달라질 수도 있다.

### 8-7. 장애 대응과 삭제 증거는 기록이 중요하다

구성도를 만들고 자원 ID·오류 메시지·변경 명령·검증 결과를 남겨야 다른 사람이 결과를 확인할 수 있다. 실제로 하지 않은 검사를 했다고 적거나, 설정만 보고 삭제 완료로 쓰지 않는다.

## 9. 추가로 알아두면 좋은 용어

아래는 평가 질문이나 다음 학습과 연결되지만 이번에 구축한 자원은 아니다.

| 용어 | 초보자용 설명 | 필요한 상황 |
|---|---|---|
| NAT | 내부 주소와 외부 주소 사이를 변환하는 방식 | 사설 주소를 사용하는 서버의 외부 통신 |
| NAT Gateway | 프라이빗 서브넷 서버의 외부 연결 등에 쓰는 AWS 관리형 구성 요소 | 직접 공개하지 않고 외부 패키지 다운로드 |
| ALB | Application Load Balancer. HTTP 요청을 여러 대상으로 분배하는 서비스 | 웹 서버를 여러 대로 확장 |
| 대상 그룹 | ALB가 요청을 보낼 서버 등을 묶은 그룹 | 분산 대상 지정 |
| 상태 검사 | 대상이 정상인지 주기적으로 검사하는 기능 | 비정상 서버로 요청을 보내지 않도록 함 |
| Auto Scaling | 조건에 따라 인스턴스 수를 조절하는 기능 | 트래픽 변화 대응 |
| RDS | 관계형 데이터베이스 운영을 지원하는 AWS 관리형 서비스 | DB 운영 부담 감소 |
| S3 | 객체 단위로 파일을 저장하는 서비스 | 이미지·첨부파일 보관 |
| CloudWatch | 지표·로그·알람 등을 다루는 AWS 서비스 | 운영 상태 관찰 |
| CloudTrail | AWS API 활동 등을 추적하는 서비스 | 누가 어떤 AWS 작업을 했는지 조사 |
| NACL | 서브넷 단위의 상태 비저장 네트워크 접근 규칙 | SG와 다른 계층의 제어 |
| 단일 장애 지점 | 하나가 고장 나면 전체 서비스가 영향을 받는 지점 | 서버 한 대 구성 |
| 병목 | 전체 처리 속도를 제한하는 부분 | CPU·DB·디스크 등 분석 |
| 수직 확장 | 서버 한 대의 사양을 높임 | CPU·메모리 증설 |
| 수평 확장 | 서버 대수를 늘림 | ALB와 여러 EC2 |
| Docker | 애플리케이션 실행 환경을 컨테이너로 구성하는 도구 | 환경 재현·배포 편의 |
| IaC | Infrastructure as Code. 인프라 설정을 코드로 관리하는 방식 | 반복 생성과 변경 추적 |
| CI/CD | 변경 검사·배포 과정을 자동화하는 접근 | 수동 배포 반복 감소 |

Docker는 EC2나 VPC를 대체하지 않는다. EC2 안에서 컨테이너로 Nginx를 실행할 수도 있고, 네트워크·보안 설정은 여전히 필요하다.

## 10. 다음 공부 순서

1. **지금 한 작업을 말로 설명하기:** EC2·VPC·서브넷·IGW·라우팅·SG·IAM을 각각 한 문장으로 설명한다.
2. **요청의 흐름 설명하기:** 브라우저에서 EC2까지 가는 조건과 응답 경로를 설명한다.
3. **오류를 단계별로 나누기:** 네트워크, 인증, 서비스 실행 문제를 구분한다.
4. **간단한 웹 앱 배포하기:** 이후 별도 실습에서 Python 웹 앱을 실행하고 Nginx와 연결해본다. 기본 페이지보다 데이터 처리와 배포의 관계를 이해하기 좋다.
5. **HTTPS와 도메인 이해하기:** 인증서와 암호화의 역할을 익힌다.
6. **재현 가능한 운영 익히기:** 서비스 자동 시작, 로그, 백업, 이후 Docker·IaC 순으로 확장한다.

현재 실습 자원은 이미 삭제했다. 이 자료를 읽기 위해 AWS 자원을 다시 생성할 필요는 없다.

## 11. 스스로 설명해볼 질문과 답의 핵심

| 질문 | 답의 핵심 |
|---|---|
| 내 노트북은 Windows인데 왜 ubuntu가 나왔을까? | SSH 접속 후 명령을 실행하는 컴퓨터가 Ubuntu EC2이기 때문 |
| 왜 SSH는 22, 웹은 80으로 나눴을까? | 서로 다른 서비스를 구분하고 접근 대상을 달리하기 위해 |
| IGW가 있는데 왜 라우팅도 설정했을까? | 출입구와 그 출입구로 보낼 경로 규칙은 별개이기 때문 |
| 10.0.1.165로 집에서 바로 접속하지 않은 이유는? | 사설 주소이며 인터넷에서 직접 접근하는 주소가 아니기 때문 |
| 내가 겪은 SSH 오류는 AWS 권한 문제였을까? | 아니요. Windows 개인 키 파일 ACL 문제 |
| localhost 성공만으로 외부 접속을 증명할 수 있을까? | 아니요. 외부에서 별도 접속해야 함 |
| HTTPS 아웃바운드 성공이면 내 서버도 HTTPS 제공 중일까? | 아니요. 외부 사이트로 요청한 것과 내 서버의 HTTPS 제공은 별개 |
| EIP가 없는데 퍼블릭 IP는 왜 있었을까? | EC2에 자동 할당된 퍼블릭 IPv4를 사용했기 때문 |
| 삭제된 EC2가 목록에 보이면 아직 실행 중일까? | 아니요. 종료됨 상태를 확인해야 함 |
| 내 미션의 최종 결과는 무엇인가? | 직접 구성한 서버 환경의 웹 응답 검증과 근거 기록, 실습 자원 정리 |

핵심 목표는 용어를 모두 암기하는 것이 아니라, **웹 요청이 어떤 조건을 거쳐 처리되는지와 실패했을 때 무엇을 확인할지 설명하는 것**이다.
